## LinkedIn: switched from UploadPost to native personal-profile posting

Originally routed through UploadPost.com (see `DISTRIBUTION_AGENT.md`) because LinkedIn's own Marketing/Community Management API requires applying as a partner. Attempted the native **Company Page** route instead on 2026-10-01, which hit a real blocker:

**Company Page creation requires a minimum number of connections on the creating LinkedIn account.** The account being used had 0 connections, and got "Feature not available — You don't have enough connections to create a LinkedIn Page." LinkedIn doesn't publish an exact current threshold; the only real fix is organically connecting with real people (not something to automate or fake — that risks the account itself getting flagged, and this requirement exists specifically to deter spam/bot accounts from standing up fake business presences).

**Decision: switched to posting via the personal profile instead, using the `w_member_social` OAuth scope.** This is self-serve — no partner review. Confirmed via LinkedIn's own developer docs (developer.linkedin.com/documents/share-api).

**Correction, same day:** initially assumed this also avoided the Company Page requirement entirely — wrong. LinkedIn's own Help article ("Associate an app with a LinkedIn Page," linkedin.com/help/linkedin/answer/a548360) confirms **a LinkedIn Page is required to create any developer app at all**, regardless of which API product/scope is used afterward. There is a "default page" exception, but it's scoped specifically to EEA/Switzerland members accessing the Member Data Portability API — confirmed not applicable here (no autocomplete appeared for this US-based account). "Showcase page" also doesn't help — it explicitly requires an existing parent Company Page to attach to. So the connections-threshold blocker on Company Page creation (above) still blocks LinkedIn entirely, even for personal-profile-only posting. Real options: (1) build genuine connections on this account until Page creation unlocks, or (2) use a different LinkedIn account that already has established connections to create the Page.

**Company Page requirements, fuller picture.** LinkedIn doesn't publish an exact connections number — described only as needing "several first-degree connections." But connections isn't the only gate; all of these are required:
- **Current employee status**: the creating account's profile Experience section must list a position at the company. Already satisfied here ("AI Marketing at Serfis AI" is listed).
- **Company email address**: a non-consumer-provider domain (not gmail/yahoo/etc.) not already used by another LinkedIn Page. `utdcapstone@serfis.ai` should qualify — this checks domain uniqueness/type, not live DNS, so it doesn't matter that `serfis.ai` isn't an actual registered website (see the Pinterest section above for that same finding).
- **Profile Strength rated "Intermediate" or "All-Star"** — a separate, checkable gate on the creating account's own profile completeness, independent of connection count. Not yet verified for this account.
- **Some first-degree connections** — no fixed number; 0 is clearly not enough.
- **Workplace verification (new gate, 2026-10-02):** the "not enough connections" error was replaced by *"Please verify your workplace before creating a LinkedIn Page"* with a Verify button, so the connections gate appears cleared and this is now the blocking one. It confirms you're genuinely affiliated with the employer listed on your profile (typically via a code sent to a work email on the company's domain). Open question whether `utdcapstone@serfis.ai` can receive that code.
- **Account age (unconfirmed factor):** this LinkedIn account was registered September 17, 2026, about two weeks old as of 2026-10-02. LinkedIn doesn't document an age requirement for Page creation, but a two-week-old account with 0 connections is plausibly part of why the gate is closed. Giving it a few more weeks of real use and genuine connections costs nothing and may help.

Action item: check the account's Profile Strength rating (LinkedIn shows this on the profile itself) and fill out any missing profile sections to reach Intermediate/All-Star, in parallel with building real connections — both are required, not just connection count.

## Reddit: commercial API terms and content-policy risk

Reddit's Data API Terms distinguish commercial from non-commercial use, and the distinction is about whether the API is used in connection with a business at all — not specifically whether you're serving third-party clients. Two scenarios, both relevant to how this tool might be used:

- **Agency use (posting on behalf of clients)** — plausibly commercial use under Reddit's terms as currently understood. The `SETUP.md` "script app" registration is the free/self-serve path; genuinely commercial use is meant to go through a different arrangement with Reddit. Not yet resolved which category this actually falls into — needs a firsthand read of Reddit's current terms (`redditinc.com/policies/data-api-terms` — this environment is blocked from fetching Reddit's own domains directly, so it hasn't been verified against the live text in this session).
- **Own-company use (posting your own content only)** — still technically business use of the API, but a much smaller volume/risk profile than agency use. Reddit's actual enforcement has historically been volume/rate-driven (aimed at heavy scraping), so low-volume posting for one company likely stays within free-tier limits even though it's not strictly "personal" use.

**Separate from API tier entirely**: Reddit's content policy and individual subreddit rules (commonly known as something like a "10% rule" against self-promotion) apply identically regardless of API commercial classification. An account posting marketing/client video content without genuine community participation risks being removed or banned by subreddit moderators — this is a moderation risk, not an API terms-of-service risk, and it's arguably the more likely thing to actually bite in practice. It applies the same whether the content is a client's or the operating company's own.

**Resolved 2026-10-01 — this is commercial use, and Reddit requires explicit written approval for it, not just a script-app registration.** Read Reddit's Responsible Builder Policy (support.reddithelp.com/hc/en-us/articles/42728983564564) directly (pasted by the user; this environment can't fetch Reddit's own domains). It states plainly: *"If you'd like to use Reddit data for commercial purposes, you'll need to get explicit written approval."* The policy's intro also applies this to everyone, not just Devvit builders: *"You must request access and get explicit approval before accessing any Reddit data through our API."* Posting a business's marketing video content is commercial use — the free "script" app type created at reddit.com/prefs/apps (done 2026-09-30/10-01) gets working credentials, but using them for this purpose without the separate written approval is a real policy violation, not a gray area.

**Possible dealbreaker found 2026-10-01 — new Data API apps may be scoped to moderation use only.** Official Reddit wiki (reddit.com/r/reddit.com/wiki/api, last revised ~5 months before this check): *"The official way to develop apps on Reddit is by using Reddit's Developer Platform... Some apps are still running on our legacy Data API. If you have **a valid moderation use case**, you should submit a request to create new apps with Reddit's Data API."* That phrasing specifically scopes new Data API app approval to moderation use cases. Our use case — a business posting its own marketing video content — is not moderation, and this wiki page doesn't describe any other approved path for new Data API apps.

This doesn't necessarily invalidate the commercial-use ticket already submitted (see "Status" below) — that's a separate request/ticket type, and its outcome is the actual authoritative answer for whether Reddit will grant this use case at all. But it's a real risk this gets denied specifically because it isn't moderation-related, independent of the reCAPTCHA issue blocking app creation itself. **If the ticket comes back denied for this reason, Reddit may need to be dropped from the platform list entirely** — there's no indication in current policy of an alternate approved path for a non-moderation, business-content-posting use case.

**New deprecation timeline found 2026-10-01**, via developers.reddit.com/app-registration: Reddit is retiring the classic `prefs/apps` script-app system. *"Starting January 12, 2027, we'll begin removing API access for apps and users that haven't registered or engaged with the Reddit Developer Platform Team. Remaining public API access will end in March 2027."* A **separate registration step** (not the same as creating the script app) is required to keep API access working past that date — register the app's Client ID at developers.reddit.com/app-registration once it exists. A $1,000 porting bounty is available for registering by November 30, 2026. **Not yet done — blocked on first actually creating the script app** (see reCAPTCHA issue below). Action item once that's unblocked: create the app, then immediately register it here too, not just at `prefs/apps`.

## Pinterest: requires a business account, mandatory app review, and terms worth reading

Pinterest's Developer API (v5, what `PinterestAdapter` uses) requires the connected account to be a **Business account**, not a personal one — same pattern as Instagram's Business/Creator requirement. Conversion is free and instant (Settings → Account settings → Convert to business account), not an approval process, but it's a real prerequisite: a personal account won't authenticate through the OAuth flow in `SETUP.md`/`get_pinterest_token.py`. Not yet verified firsthand against a live account in this session — confirm by just running the OAuth flow, which will either work or prompt for conversion.

Separately: Pinterest access tokens expire (historically ~30 days), and `PinterestAdapter` doesn't currently handle refresh — `get_pinterest_token.py` has to be rerun manually to get a new token when it lapses. Same category of issue as Instagram's 60-day token expiry, just not yet automated for either.

**Mandatory app review — a real gap the original walkthrough missed.** Pinterest's Developer and API Terms of Service, Section 2.3: *"You must submit your application, integration, or interface to Pinterest for review and approval prior to distribution to End Users **or commencement of use**."* Unlike Instagram/Facebook (where review is only required for apps requesting access beyond your own account/Page), this phrasing applies to commencing use at all, not just public distribution. Getting an access token via `get_pinterest_token.py` will work technically; using it beyond initial testing without submitting for Pinterest's review would be a real ToS violation, not just a formality. `SETUP.md` now flags this — actually submitting for review hasn't been done.

**One thing worth knowing, not a problem**: Pinterest's Developer Guidelines explicitly prohibit blanket auto-posting — *"if your app allows end users to schedule Pin publishing, the end user must choose each Pin to be published."* This is a real compliance requirement, and it's already satisfied: the approval gate in `distribute()` (see `DISTRIBUTION_AGENT.md`) requires exactly this — explicit per-post human confirmation, never a blanket auto-approve. Built before this was known to be a Pinterest requirement specifically, not because of it, but it happens to be exactly what Pinterest's terms demand.

Lower relevance for this use case: the data-privacy/CCPA/deletion obligations (Section 4 of their terms) govern *pulling* Pinterest Data (analytics, audience data) back out — since this pipeline only posts, never reads Pinterest Data, these mostly don't apply unless a future Pinterest analytics feature gets added. Same with the "publishing content" linking-back rules, which govern apps that *display* Pinterest content elsewhere, not apps that post content *into* Pinterest.

**A second, earlier gate found 2026-09-28 — "Trial access," separate from the ToS review above.** Pinterest's developer console now splits apps into a **Trial** and a **Standard** access tier. A newly created app starts in Trial, and while "Trial access pending":
- The **app secret key is withheld entirely** — shown as "Unavailable while trial access pending" — which blocks the standard OAuth flow (`get_pinterest_token.py`) since that needs the secret.
- A quick "Generate Access Tokens" shortcut is available, but it only grants **read-only** scopes (`pins:read`, `boards:read`, `user_accounts:read`, `ads:read`, `catalogs:read`) — no `pins:write`, so it's unusable for posting.
- Even if a token were obtainable, the "Writing standard Pins" capability under Trial is documented as **"Visible only to the user who creates them"** — i.e., not actually public. Real distribution needs **Standard** access, not just an approved Trial.

Filled out the app's Details tab (name, company, website/app link, privacy policy link, app purpose) — that's the only visible next step; there's no separate "submit" action beyond having Details complete. Whether/how long Trial→Standard approval takes is unknown — this is a wait state, not something to configure around. **Nothing works for actual posting until this clears**, and once it does, the Section 2.3 review requirement above still applies before relying on it beyond testing.

**Sandbox is not a workaround, checked 2026-09-30.** Pinterest's Sandbox environment (developers.pinterest.com/docs/developer-tools/sandbox/) doesn't bypass the Trial access wait — it still requires "Trial or Standard access tier" to use at all. More importantly, **Sandbox explicitly cannot create video Pins** ("Create video Pins" is listed as unsupported), so even once Trial access clears, Sandbox specifically can't be used to test this pipeline's actual use case (posting video content). No early-testing path exists here; the only route forward is the real Trial→Standard flow.

## `.env` / credentials management

Current state: each machine running this code needs its own `.env`, created locally from `.env.example` and filled in by hand (never committed — `.gitignore` covers it, and `distribution_agent/__init__.py` auto-loads it via `load_dotenv()` as of 2026-09-24). This works for a single person on a single machine, but doesn't yet have an answer for:

- **Another teammate's machine** — they'd repeat the same manual setup with their own credentials, or need the same production credentials shared through a password manager (never via git, Slack, or email in plaintext).
- **A real deployment target** (a server, a scheduled job, a PaaS, CI) — `.env` as a file is a local-dev convenience only. A production deployment should set real environment variables through whatever mechanism that platform provides (a cloud secrets manager, a PaaS's config-vars dashboard, GitHub Actions Secrets, `docker run --env-file`, etc.) rather than shipping a `.env` file to that environment at all.
- **No shared secrets vault yet** — if the team ends up needing the same production credentials across multiple people/machines, that's the point where a proper secrets manager (1Password, Doppler, Vault) becomes worth setting up rather than ad hoc file copies.

Nothing broken today, but this is unresolved for any use beyond "one person, one machine."

## Scaling

Several parts of the current design assume low volume and a single human operator; none of this is broken, but each is a real ceiling if usage grows:

- **The approval gate is a hard per-post, per-platform human checkpoint.** That's a deliberate safety choice (see `DISTRIBUTION_AGENT.md`), but it means throughput is bounded by how fast a human can say yes — there's no batch-approval mechanism today. Scaling to many videos/day across many clients would need a real approval UI (a dashboard, a queue), not just a custom `approve` callback.
- **QC scoring is human-in-the-loop (Claude doing visual review), not automated CV**, for hook, branding, safe zone, pacing, and CTA — only duration, resolution, loudness, and technical quality (blur/noise/blockiness) are actually measured by code. Higher video throughput would bottleneck on review time unless those remaining metrics get automated.
- **Per-platform rate limits and token lifecycles get harder to manage at volume** — Instagram's ~60-day token refresh and YouTube's 7-day Testing-mode window are manageable manually for one account each; multiplied across many client accounts (the agency use case), this becomes real operational overhead without an automated refresh job.
- **UploadPost's pricing scales with connected "profiles"** — the free tier caps at 2 profiles and 10 uploads/month; serving multiple clients through UploadPost (LinkedIn/TikTok) means paying for a higher tier as the client count grows (see `SETUP.md` for current pricing).
- **The QC Review Desk dashboard's database has a hard cap of 5,000 documents total** (an artifact database platform limit, not something this project controls) — fine for the current handful of logged evaluations, worth remembering if evaluation volume grows substantially; would need pruning/archiving old evaluations rather than keeping every one forever.
- **No retry/queue infrastructure** — `distribute()` is a synchronous, in-process call with no resumption if the process dies mid-run. Fine for manual/interactive use; not fine for an unattended high-volume pipeline.

None of these need solving now — they're the natural next set of problems once this moves from "one person testing manually" to "a team running this regularly at real volume."
